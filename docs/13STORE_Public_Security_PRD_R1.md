# ข้อกำหนดแพลตฟอร์ม Digital Twin for Public Security

13STORE • PRD R1 • 17 ตุลาคม 2026 • ร่างสำหรับวางแผนพัฒนา

เจ้าของผลิตภัณฑ์: 13STORE | ผู้อ่าน: Product Owner, UX/UI, ทีมพัฒนา, ทีมเชื่อมอุปกรณ์ และทีมสาธิต

เอกสารนี้กำหนดแพลตฟอร์มสำหรับรับเหตุ ตรวจสอบสถานการณ์ ประสาน UAV และ UGV ที่รองรับ และรวบรวมผลการปฏิบัติงานบนแผนที่พื้นที่เดียวกัน เป้าหมายแรกคือการสาธิตที่ตรวจสอบได้และโครงการนำร่องในพื้นที่กำหนด ข้อกำหนดทั้งหมดเป็นสิ่งที่เสนอให้พัฒนา ไม่ใช่การยืนยันว่าระบบหรืออุปกรณ์ปัจจุบันรองรับแล้ว

## 1 เป้าหมายผลิตภัณฑ์

เจ้าหน้าที่ต้องตอบคำถามได้ว่า เกิดอะไรขึ้น ที่ไหน ข้อมูลใหม่แค่ไหน มีอุปกรณ์ใดพร้อมใช้ ใครอนุมัติภารกิจ และผลล่าสุดเป็นอย่างไร โดยไม่ต้องสลับหลายระบบเพื่อประกอบภาพสถานการณ์

Digital Twin ในผลิตภัณฑ์นี้หมายถึงแบบจำลองพื้นที่และทรัพย์สินที่ผูกกับรหัสอุปกรณ์ ตำแหน่ง เหตุการณ์ และสถานะตามเวลา การมีภาพเมือง 3 มิติอย่างเดียวไม่ถือว่าครบตามนิยามนี้ รุ่นแรกยังไม่อ้างการจำลองเชิงฟิสิกส์หรือการทำนายเหตุการณ์

โจทย์นำร่องที่เสนอ: ตรวจสอบสัญญาณผิดปกติในพื้นที่สาธารณะหรือพื้นที่ดูแลของหน่วยงาน เช่น อาคารบริการ ศูนย์ขนส่ง หรือพื้นที่จัดงาน โดยเจ้าหน้าที่เป็นผู้ประเมินเหตุและอนุมัติการตอบสนอง

ใช้ขอบเขตองค์กรและพื้นที่กับทุกคำขอข้อมูลและคำสั่ง การควบคุมแต่ละอุปกรณ์มีผู้ถือสิทธิ์หลักหนึ่งราย การส่งมอบสิทธิ์ต้องมีประวัติ หลีกเลี่ยงการแย่งควบคุมระหว่างศูนย์กับเจ้าหน้าที่ภาคสนาม

## 4 เส้นทางการใช้งานหลัก

1. รับเหตุจากเจ้าหน้าที่หรือแหล่งแจ้งเตือน พร้อมตำแหน่ง เวลา แหล่งที่มา และรายละเอียด
2. แสดงเหตุบน Digital Twin และเปิดกล้องหรือทรัพยากรใกล้เคียงที่เข้าถึงได้
3. Dispatcher ตรวจสอบและจัดประเภทเป็นเหตุที่ต้องดำเนินการ เหตุซ้ำ หรือการแจ้งผิด
4. เตรียมภารกิจ เลือกอุปกรณ์จากความพร้อมจริง ระบุเส้นทางหรือจุดตรวจ และผู้ปฏิบัติงาน
5. Supervisor ตรวจและอนุมัติเมื่อเงื่อนไขกำหนด ผู้ปฏิบัติงานยืนยันรับงานก่อนเริ่ม
6. ส่งคำสั่งผ่าน adapter ที่ผ่านการทดสอบ แสดงผลตอบรับจากอุปกรณ์แยกจากสถานะการส่งคำสั่ง
7. ติดตามภาพ ตำแหน่ง และเหตุขัดข้อง บันทึกการเปลี่ยนแปลงและการแทรกแซงของเจ้าหน้าที่
8. บันทึกผล ยุติภารกิจ ผูกหลักฐาน สรุปรายงาน และปิดเหตุโดยผู้มีสิทธิ์

สถานะเหตุ: New → Triaging → Confirmed → Responding → Resolved → Closed โดยมี Duplicate และ Dismissed เป็นปลายทางทางเลือก และ Reopen ต้องระบุเหตุผล

สถานะภารกิจ: Draft → Pending approval → Approved → Assigned → Executing → Completed โดยมี Rejected, Cancelled, Paused และ Failed ตามเหตุการณ์ การสั่งหยุดไม่เท่ากับยืนยันว่ารถหยุดแล้ว

สถานะคำสั่ง: Requested → Authorized → Sent → Acknowledged → Executing → Succeeded หรือ Rejected / Failed / Timed out / Unknown การขาดผลตอบรับต้องแสดง Unknown หรือ Timed out ตามเงื่อนไข ห้ามตีความว่าเสร็จแล้ว

## 6 โครงสร้าง Digital Twin และข้อมูล

โครงสร้างพื้นที่: Organization → Site → Zone → Asset โดย Building และ Floor เป็นส่วนเพิ่มเมื่อมีข้อมูลอาคารจริง แต่ละพื้นที่ต้องระบุระบบพิกัดและการแปลงจากพิกัดเฉพาะอาคารสู่แผนที่กลาง ห้ามนำค่าความสูงคนละฐานอ้างอิงมาแสดงเสมือนตรงกัน

| Entity      | ข้อมูลสำคัญ                                                                                   |
| ----------- | --------------------------------------------------------------------------------------------- |
| Site / Zone | geometry, coordinate reference, ขอบเขตและข้อจำกัดพื้นที่, เจ้าของข้อมูล                       |
| TwinAsset   | asset ID, geometry/model reference, device bindings, source, version, updated time            |
| Device      | model, adapter version, capabilities, health, control owner, site ID                          |
| Telemetry   | device ID, source time, received time, sequence, position, accuracy, battery, quality         |
| Incident    | source, location, type, severity, status, owner, related alerts, timestamps                   |
| Mission     | incident ID, device ID, operator, plan version, approval, status                              |
| Command     | command ID, idempotency key, issuer, expiry, payload reference, acknowledgement and outcome   |
| Evidence    | incident ID, object reference, capture time, source, checksum, access policy, retention class |
| AuditEvent  | actor, action, object, before/after reference, request ID, time, result                       |

ความแม่นยำตำแหน่งและอายุข้อมูลต้องเป็นข้อมูลระดับแรกของ UX/UI ตำแหน่งไม่แน่นอนให้แสดงวงคลาดเคลื่อนหรือป้ายคุณภาพ ไม่วางจุดอย่างแม่นยำเกินข้อมูลจริง

## 7 สถาปัตยกรรมที่เสนอ

ส่วนติดต่อผู้ใช้ Command Center และ Mobile ติดต่อ API กลาง ซึ่งจัดการ identity, incident, mission, approval, evidence และ audit แยกบริการรับ telemetry และกระจาย event เพื่อไม่ให้ภาพสดทำให้การจัดการเหตุช้าลง ภาพวิดีโอผ่าน media gateway แยกจากคำสั่งควบคุม

เชื่อมอุปกรณ์ผ่าน Edge Gateway และ Device Adapter ในพื้นที่ปฏิบัติงาน แต่ละ adapter ประกาศ capabilities, หน่วยข้อมูล, protocol version, ข้อจำกัด และพฤติกรรมเมื่อขาดการเชื่อมต่อ ตัวควบคุมยานรับผิดชอบวงควบคุมการเคลื่อนที่และพฤติกรรม fail-safe เฉพาะยาน ระบบเว็บเป็นส่วนสั่งภารกิจและกำกับดูแล

SIYI เป็นหนึ่งในชุดอุปกรณ์เป้าหมาย ต้องสำรวจรุ่นจริง SDK/API สิทธิ์ใช้งาน firmware และเส้นทางภาพ/ข้อมูลก่อนยืนยัน ข้อกำหนดนี้ไม่ยืนยันว่า SIYI มี autonomy หรือ UGV integration ครบในตัว และยังไม่เลือก protocol ที่ผูกกับอุปกรณ์โดยไม่มีหลักฐาน

การติดตั้งเสนอได้ทั้งศูนย์ข้อมูลของลูกค้าและ cloud โดยตัดสินใจหลังทราบเครือข่ายและนโยบายข้อมูล ไม่อ้างว่าข้อมูลอยู่ไทยทั้งหมดจนตรวจเส้นทาง cloud, relay, telemetry และบริการบุคคลที่สามครบ

## 8 ความปลอดภัยการปฏิบัติงานและข้อมูล

แยกปุ่ม Pause mission, Stop request และ Emergency stop ตามความสามารถจริง Emergency stop ทางกายภาพและการควบคุมในพื้นที่ต้องทำงานได้โดยไม่พึ่งหน้าเว็บ เมื่อเครือข่ายหายให้ใช้นโยบายที่ทดสอบเฉพาะยาน เช่น รถหยุดในสภาพที่ปลอดภัย ส่วน UAV ต้องกำหนดตาม flight controller และสภาพแวดล้อม ไม่ใช้พฤติกรรมเดียวกันกับทุกอุปกรณ์

ใช้การยืนยันตัวตนตามความเสี่ยง เข้ารหัสการสื่อสาร จัดการ secrets แยกจากโค้ด จำกัดการส่งออกและกำหนดนโยบาย retention รายประเภทข้อมูล ประวัติ audit ต้องตรวจจับการแก้ไขได้และทดสอบ restore ก่อนนำร่อง ค่า checksum ช่วยตรวจความคงเดิมของไฟล์แต่ไม่ใช่คำรับรองการรับฟังพยานหลักฐานโดยตัวมันเอง

กำหนดขั้นตอนลบข้อมูลตามนโยบายลูกค้าและข้อกำหนดที่ทีมกฎหมายตรวจแล้ว ไม่ตั้งระยะเก็บข้อมูลตามกฎหมายเองในร่างนี้ หลีกเลี่ยงนำข้อมูลบุคคลจริงมาใช้ในบูท

## 9 เป้าหมายคุณภาพและการวัด

ค่าต่อไปนี้เป็นเป้าหมายทดสอบเสนอ ไม่ใช่ผลที่ทำได้แล้ว ต้องระบุ hardware, network, จำนวนอุปกรณ์ และรูปแบบโหลดก่อนทดสอบ

| ตัวชี้วัด                  | เป้าหมายเบื้องต้น                     | วิธีวัด                                                                           |
| -------------------------- | ------------------------------------- | --------------------------------------------------------------------------------- |
| การแสดงเหตุหลัง server รับ | p95 ไม่เกิน 2 วินาที                  | timestamp รับ event เทียบ UI render ภายใต้โหลดนำร่อง                              |
| การตรวจ telemetry เก่า     | ค่าเริ่มต้นเสนอ 5 วินาทีสำหรับรถสาธิต | ตัด feed ตรวจ last seen, ป้าย stale และการบล็อกคำสั่ง ปรับตาม rate ของอุปกรณ์จริง |
| คำสั่งซ้ำ                  | ไม่เกิดการสั่งงานซ้ำจากการ retry      | ส่ง request เดิมซ้ำและตรวจผลที่ adapter และอุปกรณ์                                |
| Audit ของคำสั่งสำคัญ       | ครบทุกคำสั่งในชุดทดสอบ                | เทียบ request, approval, acknowledgement, outcome                                 |
| การป้องกันข้ามพื้นที่      | ปฏิเสธทุกกรณีในชุดทดสอบสิทธิ์         | ทดสอบทั้ง API, media URL, evidence และ websocket                                  |
| ผลทางปฏิบัติการ            | วัด baseline ก่อนกำหนดเป้าลดเวลา      | เวลาแจ้งถึงตรวจสอบ ตรวจสอบถึงอนุมัติ และอนุมัติถึงเริ่มภารกิจ                     |

แยก latency ภาพสดออกจาก latency คำสั่งและ latency หน้าจอ ห้ามนำตัวเลขใดตัวเลขหนึ่งไปอ้างแทนประสิทธิภาพทั้งระบบ

## 10 แผนพัฒนาและประตูส่งมอบ

1. Discovery: เลือกพื้นที่นำร่อง ผู้ใช้งานจริง รุ่นอุปกรณ์ และชุดข้อมูล กำหนดผู้รับผิดชอบแต่ละส่วน ผลส่งมอบคือ capability matrix และสถานการณ์ทดสอบที่อนุมัติ
2. UX Prototype: ทำหน้าสถานการณ์ เหตุ ภารกิจ และ replay ด้วยข้อมูลจำลอง ทดสอบให้เจ้าหน้าที่หาเหตุ ตรวจความพร้อม และส่งขออนุมัติได้โดยไม่ต้องอธิบายแต่ละปุ่ม
3. Connected Demo: เชื่อมกล้องและ UGV ที่ยืนยันแล้ว ทดสอบสิทธิ์ควบคุม การหยุด การขาดเครือข่าย และการกลับมาเชื่อมต่อ UAV ยังเป็น static/simulated จนผ่านการทดสอบแยก
4. MVP Pilot: เพิ่มงานประจำวัน audit, export, backup/restore และอบรมผู้ใช้ ทดสอบการปฏิบัติการในพื้นที่จำกัดก่อนขยาย
5. Release Review: เจ้าของผลิตภัณฑ์ ผู้ปฏิบัติงาน และผู้รับผิดชอบ integration ลงนามรับข้อจำกัดที่เหลือ ไม่มีวันส่งมอบหรืองบประมาณยืนยันจนประเมินทรัพยากรและอุปกรณ์จริง

## 11 ชุดตรวจรับหลัก

- รับเหตุซ้ำแล้วรวมได้โดยไม่ทำหลักฐานต้นฉบับหาย
- ผู้ไม่มีสิทธิ์ส่งคำสั่งไม่ได้ แม้เรียก API โดยตรง
- เปลี่ยนเส้นทางหลังอนุมัติแล้วระบบบังคับทบทวนใหม่
- ตัด network ระหว่างภารกิจ เห็นสถานะไม่แน่นอน และอุปกรณ์เข้าสู่พฤติกรรมที่กำหนดไว้
- เชื่อมต่อกลับแล้วไม่รันคำสั่งเก่าหรือเริ่มภารกิจเอง
- ล็อกควบคุมเมื่อมีผู้สั่งพร้อมกัน และบันทึกการส่งมอบสิทธิ์
- การหยุดมีสถานะรอผลและผลยืนยันแยกกัน ทดสอบปุ่มทางกายภาพตามแผนเฉพาะอุปกรณ์
- Replay ไม่สามารถส่งคำสั่งไปอุปกรณ์จริง
- ส่งออกรายงานแล้วตามกลับไปยัง incident, mission และ evidence ได้
- กู้คืนข้อมูลจาก backup แล้วตรวจความครบของเหตุและหลักฐานตามขอบเขตที่กำหนด

## 12 ข้อมูลที่ต้องยืนยันก่อนล็อกขอบเขต

พื้นที่และผู้ซื้อกลุ่มแรก จำนวนผู้ใช้และอุปกรณ์พร้อมกัน รุ่น SIYI/กล้อง/flight controller/UGV driver, firmware, SDK/API ที่เข้าถึงได้ ข้อมูลแผนที่และสิทธิ์ใช้โมเดล 3D โครงข่ายสื่อสาร ผู้อนุมัติภารกิจ นโยบายข้อมูล รูปแบบติดตั้ง และทีมที่จะรับผิดชอบบริการหลังส่งมอบ
