# คอนเซปและ UXUI แพลตฟอร์ม Digital Twin for Public Security

13STORE • Concept R1 • 17 ตุลาคม 2026 • ร่างสำหรับออกแบบและนำเสนอ

ผู้อ่าน: ทีม UX/UI, ทีมพัฒนาแพลตฟอร์ม, ทีมการตลาด และทีมสาธิต

เสนอแพลตฟอร์มที่ทำให้ศูนย์ปฏิบัติการเห็นเหตุการณ์ พื้นที่ เจ้าหน้าที่ และยานไร้คนขับในมุมมองเดียว โดยใช้ Digital Twin เป็นพื้นที่ทำงานหลัก ผู้ชมต้องเข้าใจว่าระบบช่วยตรวจสอบและประสานการตอบสนองอย่างไร ไม่จำเป็นต้องเข้าใจชนิดบอร์ดหรือสายเชื่อมต่อก่อน

เอกสารนี้เป็น design brief พร้อมรายละเอียดหน้าจอและบทสาธิต ไม่ใช่ภาพหน้าจอของซอฟต์แวร์ที่มีอยู่แล้ว ข้อความ ตัวเลข และเหตุการณ์ตัวอย่างทั้งหมดเป็นข้อมูลจำลอง

## 1 ภาพจำและข้อความนำเสนอ

ชื่อประเภทผลิตภัณฑ์: Digital Twin for Public Security

ข้อความนำเสนอ: เห็นสถานการณ์ เชื่อมการตอบสนอง ติดตามทุกภารกิจ

คำอธิบายสั้น: แพลตฟอร์มเชื่อมข้อมูลพื้นที่ กล้อง เจ้าหน้าที่ UAV และ UGV ที่รองรับ เพื่อช่วยตรวจสอบเหตุ อนุมัติภารกิจ และติดตามผลจากศูนย์ควบคุมเดียว

ความสัมพันธ์กับ BUILD YOUR OWN: ชุดสร้างระบบเปิดให้ผู้พัฒนาทำยานและอุปกรณ์ของตัวเอง ส่วนแพลตฟอร์มนี้เป็นตัวอย่างการนำอุปกรณ์ที่เชื่อมต่อผ่านการทดสอบแล้วไปใช้งานด้านความปลอดภัยร่วมกัน ไม่สื่อว่าต่ออุปกรณ์ใดก็ใช้งานได้ทันทีโดยไม่มี integration

## 2 สถานการณ์หลักสำหรับบูท

พื้นที่จำลองคือศูนย์บริการสาธารณะ มีอาคาร ลานจอด ทางเดิน จุดกล้อง และจุดตรวจรถ ตั้งเหตุว่าได้รับสัญญาณผิดปกติที่ประตูบริการนอกช่วงใช้งาน ให้เจ้าหน้าที่เปิดกล้องตรวจสอบก่อนตัดสินใจ ไม่ตั้งต้นว่าบุคคลในภาพเป็นผู้กระทำผิด

เมื่อยืนยันว่าต้องตรวจพื้นที่ ผู้ควบคุมเลือก UGV ที่พร้อมใช้ ส่งขออนุมัติ และเริ่มภารกิจในขอบเขตสาธิต กล้องบนรถส่งภาพกลับมา ขณะที่แผนที่แสดงตำแหน่งและอายุข้อมูล จากนั้นแนบภาพและบันทึกผลเพื่อปิดเหตุ

UAV แสดงเป็นทรัพยากรเสริมในฉาก หากยังไม่มีการบินและส่งข้อมูลจริง ให้ระบุ SIMULATED ที่ตัวอุปกรณ์ ภาพวิดีโอ และ timeline เสมอ บูทไม่สาธิตบินจริงโดยอนุมานจากโมเดลตั้งโชว์

## 5 หน้าจอที่ต้องออกแบบ

### S01 Situation overview

เมื่อเปิดระบบ เห็นพื้นที่ที่ได้รับสิทธิ์ เหตุที่ยังเปิด และอุปกรณ์ที่พร้อมจริง ค่าเหตุเปิด อุปกรณ์พร้อม และภารกิจดำเนินอยู่เป็นตัวเลขประกอบ ไม่แย่งพื้นที่จากแผนที่ คลิกเหตุบนแผนที่หรือคิวแล้วเปิดข้อมูลเดียวกันในแผงขวา มีปุ่มสลับ 2D/3D และตัวกรองชนิดอุปกรณ์

สถานะที่ต้องออกแบบ: ไม่มีเหตุ, หลายเหตุพร้อมกัน, โหลดโมเดลไม่สำเร็จ, แผนที่ไม่มีข้อมูล และ telemetry เก่า โหมด 2D ยังทำงานได้เมื่อโมเดล 3D เปิดไม่ได้

### S02 Incident workspace

ส่วนหัวแสดง ID ประเภท ความเร่งด่วน ผู้รับผิดชอบ เวลาและตำแหน่ง แสดงหลักฐานที่ทำให้เกิดแจ้งเตือน พร้อมสถานะยังไม่ยืนยัน ข้างกันมีภาพกล้องที่เกี่ยวข้องและรายการการดำเนินการที่ผ่านมา

ปุ่มหลักเปลี่ยนตามขั้น: ตรวจสอบเหตุ → เตรียมภารกิจ → ติดตามการตอบสนอง → สรุปผล ปุ่มยืนยันว่าเป็นการแจ้งผิดและรวมเหตุซ้ำเป็นทางเลือกรอง โดยต้องบันทึกเหตุผล

### S03 Mission planner

เลือกอุปกรณ์จากรายการที่กรองตาม capability และความพร้อม แสดง battery, last seen, link status, ผู้ถือสิทธิ์ และข้อจำกัดก่อนเลือก แผนที่แสดงเส้นทางร่างแตกต่างจากเส้นทางที่อนุมัติแล้ว

ขั้นตอน: เลือกงานและอุปกรณ์ → กำหนดจุดตรวจและผู้ปฏิบัติ → ตรวจข้อจำกัด → ส่งขออนุมัติ ไม่ใช้คำว่าเริ่มภารกิจเมื่อยังเป็นเพียงการส่งคำขอ หลังอนุมัติให้ operator ยืนยันรับงานและความพร้อมก่อนเริ่มจริง

### S04 Live mission

หน้าจอรวมแผนที่ตำแหน่ง ภาพจากยาน และรายการคำสั่งพร้อมผลตอบรับ แสดงผู้ควบคุมอยู่ตลอด ปุ่มควบคุมปรับตามยานที่เลือกและ capabilities ที่ผ่านการตรวจ

ปุ่ม Pause และ Stop request แยกกัน พร้อมคำอธิบายผล การส่งคำขอหยุดต้องแสดง กำลังรอยืนยัน แล้วเปลี่ยนเป็น หยุดแล้ว เฉพาะเมื่อมีข้อมูลยืนยัน หากไม่ทราบผลให้แสดง ไม่ทราบสถานะ และแนวทางติดต่อผู้ปฏิบัติงาน ไม่ใช้ animation เพื่อแสร้งว่าอุปกรณ์หยุดแล้ว

### S05 Evidence and replay

เลือกช่วงเวลาเพื่อดูตำแหน่ง ภาพ และการกระทำร่วมกัน มีแถบ REPLAY ชัดเจน เวลาอดีตแสดงตลอด ไม่มีปุ่มส่งคำสั่งจริง ไฟล์แนบมีผู้บันทึก แหล่งที่มา เวลา และสถานะความสมบูรณ์ การดาวน์โหลดตรวจสิทธิ์และลง audit

### S06 Device and integration workspace

แสดงรายการอุปกรณ์พร้อมสถานะ Verified, Testing หรือ Simulated เป็นสถานะการเชื่อมต่อผลิตภัณฑ์ แยกจาก Online/Offline ของอุปกรณ์จริง รายละเอียดแสดง adapter version, firmware ที่ทดสอบ, คำสั่งที่รองรับ และข้อจำกัด เปิดเผยการเชื่อมต่อที่ยังไม่พร้อมอย่างตรงไปตรงมา

### S07 Field mobile

หน้ารับงานมีภารกิจ ตำแหน่ง ติดต่อศูนย์ และ action หลัก ได้แก่ รับงาน ถึงพื้นที่ และรายงานผล ออกแบบให้แตะง่าย อ่านกลางแจ้งได้ และแสดงข้อมูลรอซิงก์ การอัปโหลดซ้ำต้องไม่สร้างหลักฐานซ้ำโดยไม่จำเป็น ไม่ยกชุดควบคุมเต็มจาก desktop ลงมือถือ

## 6 ภาษาภาพ

ใช้ธีมเข้มสำหรับ command center แต่พื้นฐานข้อมูลต้องอ่านง่าย เสนอพื้นหลัง #0B1220 แผง #162235 ตัวอักษรหลัก #F1F5F9 และข้อความรอง #B6C2D1 ใช้ cyan #38BDF8 กับสิ่งที่เลือก amber #FBBF24 กับความผิดปกติ และ red #F87171 กับเหตุเร่งด่วน ทุกสีต้องมีไอคอนหรือข้อความประกอบและทดสอบ contrast ก่อนส่งมอบ

ใช้ฟอนต์ที่รองรับไทย เช่น Noto Sans Thai และฟอนต์ละตินที่เข้าคู่กัน ตัวเนื้อหา desktop ประมาณ 16 px และเพิ่มขนาดในโหมดจอแสดงผล ปุ่ม touch เสนอพื้นที่แตะอย่างน้อย 44 × 44 px พร้อมการตรวจใช้งานจริง

โมเดลอาคารเป็นสีเทาเรียบ ลดพื้นผิวที่ไม่ช่วยงาน เหตุที่เลือกมีขอบและป้ายชัด อุปกรณ์ใช้ icon ตามประเภทพร้อมชื่อสั้น แสดง route เฉพาะภารกิจที่เลือกเพื่อไม่ให้แผนที่รก หลีกเลี่ยงลูกโลกหมุน แสงวิ่งตกแต่ง และการกระพริบต่อเนื่อง

## 7 สถานะที่ต้องเห็นเสมอ

| สถานะ           | วิธีแสดง                      | พฤติกรรม                                      |
| --------------- | ----------------------------- | --------------------------------------------- |
| LIVE            | ป้ายและเวลาอัปเดต             | ใช้เมื่อ feed ใหม่ตามเกณฑ์จริง                |
| STALE / DELAYED | ป้ายสีเหลือง อายุข้อมูล       | ลดความมั่นใจของตำแหน่งและจำกัดคำสั่งตามนโยบาย |
| OFFLINE         | ป้ายตัดการเชื่อมต่อ Last seen | ไม่วาดตำแหน่งเคลื่อนต่อเสมือนสด               |
| SIMULATED       | ป้ายที่อุปกรณ์ ภาพ และข้อมูล  | แยกจากข้อมูลจริงทุกครั้ง                      |
| REPLAY          | แถบโหมดพร้อมเวลาในอดีต        | ปิดการส่งคำสั่งจริง                           |
| COMMAND PENDING | แสดงเวลาที่ส่งและรอผล         | ไม่แสดงว่าเสร็จจนได้รับผลยืนยัน               |
| CONTROL HELD    | ชื่อผู้ควบคุมปัจจุบัน         | ต้องผ่านการส่งมอบก่อนสั่งแทน                  |

หากหน้าจอมีข้อมูลจริงและจำลองปนกัน ให้แสดง MIXED DEMO ที่ระดับหน้าและติดป้ายแต่ละรายการ แทนการใช้ป้าย LIVE ใหญ่เพียงป้ายเดียว

## 8 ตัวอย่าง microcopy

- แจ้งเตือนใหม่ ยังไม่ได้รับการยืนยันจากเจ้าหน้าที่
- ข้อมูลล่าสุดเมื่อ 8 วินาทีที่แล้ว การสั่งงานใหม่ถูกพักไว้
- ส่งคำขอเริ่มภารกิจแล้ว กำลังรออุปกรณ์ตอบรับ
- ไม่ทราบผลคำสั่ง โปรดตรวจสอบกับผู้ควบคุมในพื้นที่
- เส้นทางถูกแก้ไข ต้องขออนุมัติใหม่
- คุณกำลังดูข้อมูลย้อนหลัง การควบคุมอุปกรณ์ถูกปิด
- ข้อมูล UAV ชุดนี้เป็นข้อมูลจำลองสำหรับการสาธิต

| 30–60 วินาที   | เหตุจำลองและภาพกล้อง              | เมื่อมีแจ้งเตือน เจ้าหน้าที่เปิดข้อมูลเพื่อยืนยันก่อนตัดสินใจ |
| 60–100 วินาที  | เตรียมและอนุมัติภารกิจ            | เลือกทรัพยากรที่เหมาะสมและกำหนดผู้รับผิดชอบ                   |
| 100–150 วินาที | UGV ในพื้นที่สาธิตและภาพกลับ      | คำสั่งถูกส่งไปยังอุปกรณ์ที่เชื่อมต่อแล้ว และเห็นผลตอบรับ      |
| 150–180 วินาที | Timeline และรายงานเหตุ            | ทุกขั้นติดตามย้อนหลังได้ ตั้งแต่รับเหตุจนสรุปผล               |

ก่อนรอบสาธิต reset dataset และตรวจการเชื่อมต่อ หากอุปกรณ์ขัดข้อง ให้เปลี่ยนเป็นโหมดจำลองที่ติดป้ายและแจ้งผู้ชม ห้ามเล่นวิดีโอสำเร็จรูปโดยเรียกว่าเป็นภาพสด

## 10 ความสัมพันธ์กับพื้นที่จัดแสดง

จอใหญ่แสดง Situation หรือ Live mission คอนโซลด้านหน้าใช้ตรวจเหตุและอนุมัติ ภาพรถ UGV บนหน้าจอต้องผูกกับรหัสเดียวกับรถในพื้นที่สาธิต ฝั่ง BUILD YOUR OWN แสดงชุดควบคุมและตัวถังพิมพ์ 3D เพื่ออธิบายว่าผู้พัฒนาจะสร้างอุปกรณ์ต่อยอดเข้าสู่แพลตฟอร์มผ่าน adapter และการทดสอบได้อย่างไร

ข้อความบนจอเน้นภารกิจและผลลัพธ์ ส่วนรายละเอียด protocol และ wiring อยู่บนจอเทคนิคหรือเอกสารประกอบ การจัดบูทจริงต้องอ้างอิงพื้นที่ที่แบ่งให้แพลตฟอร์ม ไม่ถือว่าได้พื้นที่ 7 × 6 เมตรทั้งหมดหากใช้ร่วมกับ DJI หรือ Altura

## 11 งานส่งต่อให้ทีมออกแบบ

ส่งมอบ design file ที่มี component library, navigation, typography, colors, status badges, device cards, incident cards, approval dialog, command status และ empty/error/loading states พร้อม prototype เชื่อม S01 → S02 → S03 → S04 → S05

ออกแบบอย่างน้อย desktop 1920 × 1080, laptop 1440 × 900, field mobile 390 × 844 และ presentation mode สำหรับจอใหญ่ ตัวอย่างเป็นขนาดออกแบบ ไม่ใช่การล็อกอุปกรณ์ที่จะซื้อ

ทดสอบกับผู้แทนเจ้าหน้าที่โดยให้หาเหตุ เลือกกล้อง ตรวจความพร้อม ส่งขออนุมัติ รับรู้ว่าข้อมูลขาด และปิดเหตุ เก็บจำนวนครั้งที่หลงทาง ขั้นตอนที่ต้องอธิบาย และเวลางานจริงก่อนปรับรอบต่อไป

## 12 หลักตรวจรับ UXUI

ผู้ใช้ต้องแยกเหตุยืนยันกับแจ้งเตือนได้ แยกส่งคำสั่งกับทำงานสำเร็จได้ ทราบว่าใครกำลังควบคุม มองเห็นอายุข้อมูล และออกจาก replay กลับสู่ปัจจุบันได้ชัดเจน ทุกหน้าไม่ควรสื่อว่าความสามารถที่ยังจำลองอยู่พร้อมใช้งานจริง
